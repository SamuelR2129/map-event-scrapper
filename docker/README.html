scraper-container

Runs all Playwright scrapers sequentially in a hardened container using Orbstack (Docker-compatible runtime on Mac). Scraped data is sent directly to a production DB via API — no filesystem bridge between host and container.

Prerequisites

Build

# From map-event-scrapper/
docker build -f docker/Dockerfile -t scraper-container .

Run

docker run --rm --init \
  --env-file .env \
  --cap-drop=ALL \
  --cap-add CHOWN --cap-add DAC_OVERRIDE --cap-add FOWNER \
  --cap-add SETUID --cap-add SETGID --cap-add SETPCAP --cap-add NET_BIND_SERVICE \
  --security-opt=no-new-privileges:true \
  --pids-limit=256 \
  --tmpfs /tmp:size=1g \
  --tmpfs /app/scraper/src/eventFiles:uid=1000,gid=1000 \
  --tmpfs /app/scraper/test-results:uid=1000,gid=1000 \
  --tmpfs /app/scraper/playwright-report:uid=1000,gid=1000 \
  --tmpfs /app/scraper/logs:uid=1000,gid=1000 \
  scraper-container
The above flags are the hardened baseline (see Security). If Chromium in an unrelated host environment stops launching, drop --cap-drop=ALL for that run.

How it works

  1. All scraper spec files run sequentially in a single VM: scrape → scrape → … → map → send to DB
  2. Scraper code is baked into the image at build time
  3. Secrets (OPENCODE_API_KEY, etc.) are passed at runtime via --env-file
  4. If a test fails, the healer (opencode agent) is invoked to fix it. It retries up to 3 times with backoff — each attempt: fix via opencode, then verify with npx playwright test. Only exits 0 if verification passes.
  5. After all tests complete, if any were fixed, commitAndPushAllChanges creates a branch (healer-auto-fix-<timestamp>), commits, pushes, and opens a PR via the GitHub API (curl). Requires git credentials in the container (SSH key mount or GITHUB_TOKEN in .env).
  6. After completion, results are in the database

Why event files and scrappers are seeded twice (Dockerfile + entrypoint)

Both src/eventFiles and src/scrappers are copied into separate seed directories at build time, then copied back into place at runtime by the entrypoint. This is intentional — the working paths cannot be trusted from the image layer.

src/eventFiles — masked by tmpfs

The run command mounts --tmpfs /app/scraper/src/eventFiles:uid=1000,gid=1000. A tmpfs mount starts empty and hides the image layer at that path, so the data baked into the image at src/eventFiles is invisible at runtime. The seed copy at /app/seed/eventFiles lives at a non-masked path, and the entrypoint restores it before npm run map and send-to-db run. Without this, the scrapers would run against an empty directory.

src/scrappers — mutated by the healer

The healer edits the spec files at runtime to fix failing tests, and the git reporter then pushes everything with git add -A up to a healer-auto-fix-<timestamp> PR branch. Seeding /app/seed-scrappers at every run's startup guarantees the scrapers are back to the exact baked/committed versions before the next run, so:

  • the test run (and the healer's verification) always exercises the pristine committed code, and
  • any diff pushed to the PR branch contains only what the healer changed, not debris from previous runs.

Why both Dockerfile and entrypoint copy

  • Dockerfile copy → snapshots state into a separate, non-masked, read-only location at build time (/app/seed and /app/seed-scrappers).
  • Entrypoint copy → restores from that safe location into the writable/masked working directories, just before use.
This makes each run hermetic: same baseline every time, regardless of tmpfs mounts or mutations, even if a container is kept alive across multiple entrypoint invocations.

Playwright MCP server (opencode)

The playwright-test MCP server gives opencode agents live browser control for scraper planning, generation, and healing. It is configured in opencode.json: 

{
  "mcp": {
    "playwright-test": {
      "type": "local",
      "command": ["npx", "playwright", "run-test-mcp-server"],
      "enabled": true
    }
  }
}

How it launches

  • Local stdio server. On opencode startup, the config above spawns npx playwright run-test-mcp-server as a child process. It must be launchable from the project root (i.e. playwright installed via npm ci and npx on PATH). The server exposes ~30 tools (browser_navigate, browser_snapshot, browser_click, generator_write_test, planner_save_plan, …) to opencode.
  • Namespacing. Every MCP tool is exposed as playwright-test/<toolName>; agent configs match them with glob patterns like "playwright-test*browser_click".
  • Main agents get none of them. The top-level "tools": { "playwright*": false } disables all Playwright tools for the main build/plan agents.
  • Subagents get allowlists. Each playwright-test-* agent re-enables its own subset of tools.
Agent Browser tools Special tools
planner navigate, click, snapshot, hover, evaluate, network, screenshot, … planner_setup_page, planner_save_plan
generator navigate, click, snapshot, evaluate, type, wait, … generator_setup_page, generator_read_log, generator_write_test
healer navigate, evaluate, screenshot, console/log, network, locator, … test_list, test_run, test_debug enabled
No browser download at runtime. The docker image ships Chromium via the Playwright base image, so npx playwright run-test-mcp-server starts without a download step. The healer inside the container runs opencode with this same config, giving it browser access to debug failing scrapers.

Healer error flow

The healer is a post-failure repair loop attached to the Playwright reporter — it is not part of the scraping path itself. This section walks the full flow end to end, from the first failing assertion to the auto-PR, including every point where it can break and what happens in each case.

End-to-end flow

  1. Failure collection. HealerReporter.onTestEnd records every non-passed, non-skipped test with its file, title, and error context (error message + code snippet).
  2. Trigger. onEnd prints the error context to stdout, then runs scripts/run-with-healer.sh once per failing test via execFileSync with the failure passed as environment variables: HEALER_TEST_FILE, HEALER_TEST_NAME, HEALER_ERROR, and PW_HEALER_RUN=1.
  3. Graceful degradation. If opencode is not on PATH, the script logs [HEALER] opencode not found — skipping healer and exits 0. The test stays broken but the pipeline continues.
  4. Fix-and-verify loop. Otherwise it runs opencode run --agent playwright-test-healer --auto with a prompt containing the failing test name, file, and error. The agent edits the spec file and verifies its own fix by re-running the single failing test with the test_run MCP tool.
  5. Verification contract. The script exits 0 only when opencode exits 0 — which, per the healer's prompt, only happens once test_run confirms the fix. Anything else counts as a failed attempt.
  6. PR or report. If every failing test healed, commitAndPushAllChanges creates branch healer-auto-fix-<timestamp>, commits, pushes, and opens a PR. If any test is still broken, the reporter logs [HEALER] X/Y still failing after healing with the survivors and opens no PR.

Recursion guard — PW_HEALER_RUN

The healer's own verification runs Playwright again (via test_run). Without a guard, a still failing verification would re-enter onEnd and spawn another healer — an infinite loop. The guard is one line: onEnd returns immediately if PW_HEALER_RUN is set. The variable is injected into the healer's environment and inherited by every Playwright process it spawns, so nested runs are never re-healed.

Retry and backoff

scripts/run-with-healer.sh allows MAX_RETRIES=3. A failed attempt sleeps before the next one, with the delay increasing by 10 s each time:

Attempt Sleep before next On failure
1 5 s retry
2 15 s retry
3 — exit 1 — "All 3 attempts exhausted"

Exit-code contract

Exit code Meaning Reporter behaviour
0 opencode succeeded and verified the fix marked healed; if all heal → commit, push, PR
1 3 attempts exhausted, still failing listed in "still failing" summary; no PR
0 — opencode missing healing skipped, never attempted quirk: marked healed, but git status is empty so the commit/PR path is a no-op

What the healer gets (prompt contract)

  • Failure data: test name, test file, and the full error message + snippet collected by the reporter.
  • Instruction: "Do not ask questions — fix the tests. The healer verifies the fix itself via the test_run tool." The agent runs non-interactively (--auto).
  • Agent config (opencode.json): mode all, model opencode/deepseek-v4-flash-free, bash: false — no shell access. It can only read files, edit them, and drive the browser/verification through the allowlisted playwright-test/* MCP tools (test_run, test_list, test_debug, browser navigate/snapshot/evaluate/click, …).
  • Scope: the prompt instructs it to run only the specific failing test, never the full suite.

Failure modes

Where it breaks Symptom Consequence Fix
Healer startup UnknownError / "Unexpected server error" agent never starts; all 3 attempts burn on backoff fix model ID — see Troubleshooting
Agent runtime ripgrep buffer / ENOENT / SQLite "Failed to execute statement" healer can't read or write state don't run with --read-only — see Troubleshooting
Verification test_run still red after the edit opencode exits non-zero → retries ×3 → still-failing summary, no PR site may be down or changed; inspect the run's trace in test-results
Browser launch Chromium fails to start without sandbox flags every verification fails regardless of the fix keep --no-sandbox --disable-setuid-sandbox (already in playwright.config.ts)
Commit / PR git push or PR POST fails (bad GITHUB_TOKEN, network) caught inside commitAndPushAllChanges; logged, non-fatal — pipeline continues check token scopes (contents:write, pull_requests:write)

Healing failures never block the pipeline

  • npm run scrape-xvfb runs with || true in the entrypoint — a non-zero Playwright exit (failed tests or failed healing) is swallowed.
  • The reporter heals in-process after the run; even a total healer failure doesn't stop npm run map or send-to-db.
  • The healer's opencode run inherits the container env (--env-file), so it uses the same API keys and can browse the same live sites as the scrapers.

Security

The container is intentionally ephemeral (removed after each run) and needs unrestricted outbound internet to scrape gig listings, so egress itself is not firewalled. Hardening focuses on limiting what an attacker gains inside the container and what leaks out:

  • No secrets in the image. .env is excluded via .dockerignore and must never be baked in; secrets reach the container only through --env-file at runtime.
  • Non-root runtime (USER node). The scraper, playwright, xvfb, and the healer all run as a dedicated non-root user with a writable home (/home/node) for node/git/opencode state.
  • Dropped capabilities. --cap-drop=ALL plus a minimal allow-list (DAC_OVERRIDE, SETUID, SETGID), combined with --security-opt=no-new-privileges:true. What each retained capability actually grants (all Linux capability(7) scoped to the container's namespace):

What each retained capability actually grants (all Linux capability(7) scoped to the container's namespace):

DAC_OVERRIDE
Bypass file read/write/execute permission checks; lets the non-root user write regardless of DAC (discretionary access control) permissions, covering git/npm/opencode writes to directories that may not carry exact ownership metadata after image-layer copies.
SETUID / SETGID
Allow changing the effective UID/GID of processes and setting setuid/setgid bits; kept for toolchains that re-exec themselves with dropped privileges.
Everything else is dropped — NET_RAW (raw/packet sockets), SYS_ADMIN (mounts, namespaces), SYS_PTRACE, SYS_MODULE, DAC_READ_SEARCH, etc. A compromised scraper process cannot load kernel modules, attach ptrace, create raw sockets for network sniffing, or reconfigure namespaces.
  • Chromium runs --no-sandbox. The container lacks SYS_ADMIN/userns, which breaks Chromium's setuid sandbox; Playwright is configured with --no-sandbox --disable-setuid-sandbox as an explicit trade-off.
  • Process limit. --pids-limit=256 constrains browser/child-process fan-out.
  • Ephemeral writes. Writable dirs (/tmp, src/eventFiles, test-results, playwright-report, logs) are tmpfs-backed, so no host state persists. The tmpfs mounts are created uid=1000,gid=1000 so the non-root node user (also uid/gid 1000 in the image) can write to them. 1000 is the uid/gid that the official Node Docker base image assigns to the node user (the first non-root user in Linux, hence the conventional 1000). A tmpfs mount starts owned by root, so --tmpfs ...:uid=1000,gid=1000 re-owns it to node at mount time; without this the container — which runs as USER node — would get EACCES/ENOENT writing to those directories.
  • Egress hardening. An attacker-influenced URL is blocked at the app layer (src/helpers/ssrf.ts: rejects private/loopback/link-local IPs, host.docker.internal and friends, plus DNS-rebinding-style internal resolutions) before any page.goto. For stronger isolation, run the container through an outbound allowlist proxy by setting HTTPS_PROXY/HTTP_PROXY in .env (also wired via --env-file).

For runtime egress allowlisting the container already reaches: the scraper target domains, bandcamp.com, api.github.com, the Google AI/Maps/Places API hosts and PRODUCTION_DB_URL.

Prompt protection

Every venue and listing site this pipeline scrapes is untrusted input. Event names, descriptions, genres, and page text are attacker-controllable — a compromised or hostile site can embed text that looks like instructions ("ignore your rules…", system-tag payloads). Anything scraped that reaches an LLM prompt is a potential prompt-injection vector. The project treats this as a defense-in-depth problem: no single layer is trusted to stop a determined attacker, but each layer raises the bar and limits the blast radius.

Threat model

Two LLM surfaces receive untrusted content:

  • Gemini data-entry helpers (aiGenerateEventDescription, aiGenerateArtistBandCampUrl, date/coordinate/dedup filters in src/helpers/ai/) — fed with scraped event fields.
  • Opencode agents (planner / generator / healer) — read live page text directly through the Playwright MCP browser tools.

The attacker's goals: make the AI write attacker-chosen content (SEO spam, links, defacement), steer the Bandcamp URL generator toward attacker-controlled URLs, or attempt exfiltration. The last one is largely moot by construction — the prompts contain no secrets and the models have no tool access beyond generating JSON text.

Layer 1 — sanitize at ingest

Every scraper must end with sanitizeAndWriteToStagingFile, which filters out non-music event types and passes each event through sanitizeEvents (src/helpers/sanitizer.ts). Three sanitizers run in sequence on every string field:

Sanitizer Strips
escapeHtml <, >, " — HTML/XSS payloads
sqlSanitizer SQL keywords (select, insert, union, exec, …), --, ;, quotes, backslashes, OR/AND
aiPromptSanitizer instruction-override phrases, role-hijack prefixes, model instruction tags

The prompt-injection layer specifically strips:

  • Override attempts: ignore / disregard / forget (previous|above|all|your) (instructions|rules|prompts), new (instructions|rules|prompt)
  • Role hijacking: system: you are, assistant: you are
  • Model instruction tags: [INST], <<SYS>>, ChatML (<|im_start|> / <|im_end|>), template syntax ({{system}}, {{user}}, {{assistant}})
Blacklists are a last resort. A determined attacker can rephrase an instruction to slip past any regex — the same caveat applies to sqlSanitizer. This layer catches the obvious copy-paste injection payloads; the layers below carry the real security weight.

Layer 2 — LLMs only ever read from disk, never from the network

Scraped data cannot reach a prompt directly from a website. Scrapers write sanitized JSON to staging-events.json on disk, and the map phase (mapAndWriteToFiles) reads that file and feeds the AI helpers. Any payload that survives Layer 1 must survive a filesystem round-trip before it can influence a model.

Layer 3 — constrained, validated AI output

  • Structured output. Every Gemini call uses responseMimeType: application/json with a responseSchema (plus zod parsing where used) — the model returns JSON, and the code checks required fields and types before trusting them.
  • Bandcamp URL generator. The prompt hard-codes exclusions (never return a previously failed URL, never duplicate a lineup artist, strict https://{slug}.bandcamp.com/ format, Australia + genre match). Even then the URL is not trusted: fetchMediaIdFromUrl re-checks it with isSafeExternalUrl before page.goto, rejects Bandcamp signup pages, and only accepts a media ID that actually exists in the DOM ([data-item-id] or og:video). A "successful" injection still lands on a real, existing artist page — not an attacker-controlled URL.
  • Description generator. Output is a single JSON string; the worst case for a poisoned input is a garbage description in the DB — no security impact.

Layer 4 — URLs as an injection channel

URL fields (eventLink, ticketLink, socialLink, banner images) go through sanitizeUrl: only http:/https:, then the SSRF blocklist (isBlockedExternalUrl). An injected link can't point at internal hosts, and outbound requests in the scraper pipeline apply the same check. See Security.

Layer 5 — validation at the API

The final gate is outside the container entirely. sendCompleteEventsToDb POSTs complete-events.json to the production API (POST /map/events/multiple, authenticated via godAccessPassword), and the server-side API validates the payload before anything reaches the database. Even if every client-side layer above is bypassed — malformed, oversized, or structurally wrong records are rejected at the boundary rather than persisted. Sanitization in this container is treated as a best-effort first pass; the API is the authoritative schema/type check.

Known gap — the opencode agents

Page text read by the planner, generator, and healer is not sanitized. Those agents browse live sites via the Playwright MCP tools and read snapshots, console messages, and network logs straight into their context. The aiPromptSanitizer does not run on that content, so a hostile page can attempt to steer the agent's behavior with embedded instructions.

Mitigations that soften (not eliminate) this gap:

  • Tool allowlists. The healer has bash: false and only file read/edit plus browser tools — agents can't execute arbitrary shell or reach other machines.
  • Scoped writes. The generator can only write into src/scrappers/, and any healer edit lands on a healer-auto-fix-* branch behind a PR — a human review gate before hostile changes could reach main.
  • Prompt hardening. The healer prompt pins the workflow ("fix the failing test, verify with test_run, never run the full suite") so injected text competes with an explicit contract rather than an empty one.

Image size

The built image is ~4.2 GB. Breakdown by layer:

Layer Size Notes
Playwright base (Chromium + system deps) ~2.7 GB mcr.microsoft.com/playwright:v1.61.1-noble
npm ci — installed dependencies ~137 MB Baked into image, includes node_modules
Opencode CLI ~178 MB Linux ARM64 binary for test self-healing
Source code (excl. host node_modules) ~2.1 MB Via .dockerignore — host node_modules excluded
Seed data backups ~1.8 MB Copied at build, restored to tmpfs at runtime
Why not smaller? The Playwright base image ships Chromium, Firefox, and WebKit (~1.2 GB of browser binaries). This is the standard trade-off for a zero-download-at-runtime sandbox.

Ripgrep config

The image and entrypoint create ~/.config/ripgrep/config (in the node user's $HOME) with --max-columns=10000. This prevents ripgrep's JSON output from exceeding its 65536-byte internal buffer when searching files with very long lines (e.g., minified HTML, WebFetch output).

Troubleshooting

Healer fails with UnknownError

If the healer crashes immediately with "UnknownError" and "Unexpected server error", the model ID in opencode.json is likely invalid. OpenCode Zen model IDs use the format deepseek-v4-flash-free, not deepseek/deepseek-v4-flash-free. The slash prefix causes the server to fail before the agent can start.

--read-only causes cascading failures

Running with --read-only breaks the healer and many tools. Specific symptoms:

Symptom Cause
Ripgrep JSON record exceeded 65536 bytes ripgrep can't write temp files, chokes on long lines
locator.innerText: Unexpected token "" healer can't write the fix to read-only src/scrappers
ENOENT: mkdir '/app/scraper/test-results' Playwright can't create output directory
UnknownError on healer start opencode can't initialize its DB in read-only ~/.local/share/opencode
Failed to execute statement SQLite can't create WAL files
Fix: Don't use --read-only. The container is ephemeral anyway — torn down after each run, so no lasting security benefit.
